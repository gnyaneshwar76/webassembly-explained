Concepts

What is WebAssembly

The short version

WebAssembly (abbreviated Wasm) is a binary instruction format for a stack-based virtual machine. It is a portable compilation target: other languages compile to it, and the result runs in any engine that implements it, in the browser or outside it.

It does not replace JavaScript. The two run in the same engine and call each other. JavaScript stays in charge of the page, and Wasm takes the heavy numeric work.

Why it exists

JavaScript is flexible, but it was not designed for work like video codecs, 3D engines or image processing. Mozilla's asm.js (2013) showed that a strict subset of JavaScript could run much faster. WebAssembly replaced that idea with a real binary format. It reached all four major browsers in 2017.

The other motive is reuse. Decades of C, C++ and Rust code can now run on the web without being rewritten.

How a module runs

  1. You write code in a language with a Wasm target.
  2. A compiler produces a .wasm file.
  3. The browser downloads it, then validates and compiles it.
  4. JavaScript instantiates the module, supplying anything it imports.
  5. JavaScript calls the module's exported functions like ordinary functions.
const { instance } = await WebAssembly.instantiateStreaming(fetch("demo.wasm"));
console.log(instance.exports.add(2, 3)); // 5

instantiateStreaming compiles while the file downloads. The server must send the application/wasm content type, which GitHub Pages does.

Core terms

Module
The compiled binary. It has no state of its own and declares what it imports and exports.
Instance
A module plus its running state: its memories, tables and imported values.
Memory
A growable buffer of raw bytes that Wasm instructions read and write. JavaScript can see the same bytes.
Table
A growable array of references, such as functions, that cannot be stored as plain bytes.
Import and export
Imports are things the module needs from outside, for example a JavaScript function. Exports are what it offers back.

The core number types are i32, i64, f32 and f64, plus vector and reference types. There is no string type. Text is stored in memory as bytes and both sides agree on how to read it.

Two formats

Every module has a compact binary form (.wasm) and an equivalent text form (.wat) that people can read and write. A tool such as WABT converts one to the other. This is the same function in both forms:

TextBinary (hex)
local.get 020 00
local.get 120 01
i32.add6a
end0b

That is the body of add(a, b): push both arguments onto the stack, add the top two values, finish. The Try it page shows the full source and bytes of a working module.

What it cannot do alone

Wasm has no direct access to the page. To change the DOM, draw on a canvas or make a network request, it calls a JavaScript function that it imported. That glue code is why tools such as Emscripten and wasm-bindgen generate a JavaScript file next to the .wasm.

Beyond the browser

The same sandboxed format runs on servers and devices. WASI (the WebAssembly System Interface) gives modules controlled access to files and clocks. Runtimes such as Wasmtime and Wasmer, and Node.js, can execute Wasm.

Versions

WebAssembly 1.0 became a W3C Recommendation on 5 December 2019. Version 3.0 was announced as complete in September 2025, adding features such as garbage collection, 64-bit memory addressing, exception handling and tail calls. Which feature works in which engine is tracked on the official feature status page.
